# 요구사항 요약

## 목적

여러 PPTX 문서를 업로드한 뒤, 슬라이드 내 텍스트와 인포그래픽 맥락을 RAG에 적재하고, 사용자의 질의에 대해 다음을 반환하는 서비스를 설계한다.

- 관련 내용의 자연어 답변
- 어떤 PPTX에 근거가 있는지
- 몇 번째 슬라이드에 관련 정보가 있는지

## 핵심 사용자

- 운영자: PPTX 업로드, 재처리, 삭제, 상태 확인
- 일반 사용자: 질문 입력, 관련 PPTX/슬라이드 확인
- 시스템 관리자: 임베딩 모델, Chroma, 저장소 상태 관리

## 범위

- PPTX 업로드 및 버전 관리
- 슬라이드 단위 파싱
- 텍스트, 표, 도형 텍스트, 노트, 이미지 OCR 결과 수집
- 슬라이드 요약 생성
- 워킹 프로세스/업무 흐름 구조 추출
- 청크 생성 및 임베딩
- Chroma 적재
- 질의 시 관련 슬라이드 반환
- 근거 기반 응답 생성
- 추출 품질 평가와 재처리 기준 관리
- 질의 유형 분류와 workflow 우선 재랭킹
- low-confidence 검수 큐 운영

## 비범위

- 완전한 문서 편집 기능
- PPTX 디자인 렌더링 품질 보정
- 고급 차트 구조 완전 해석
- 실시간 공동 편집

## 주요 가정

- 슬라이드 번호는 사용자에게 `1`부터 시작하는 값으로 보여준다.
- 인포그래픽 맥락 추출은 100퍼센트 시각 이해가 아니라, 우선 `텍스트 + 요소 구조 + OCR + 슬라이드 요약` 조합으로 해결한다.
- 워킹 프로세스 슬라이드는 `단계`, `주체`, `조건`, `예외 흐름`까지 구조화해서 다뤄야 한다.
- OCR은 비용과 정확도 이슈가 있으므로 선택 기능으로 설계한다.
- 동일 파일 재업로드는 해시 기반 중복 판정이 가능해야 한다.

## 권장 아키텍처 방향

| 영역 | 권장안 | 이유 |
|---|---|---|
| 애플리케이션 | Spring Boot | 업로드, 배치, API, 운영 분리 용이 |
| 빌드 | Gradle | 표준화 및 CI 구성 용이 |
| 벡터 DB | Chroma | 메타데이터 필터와 간단한 운영에 적합 |
| 운영 메타데이터 | PostgreSQL 또는 초기 H2 | 문서/잡/버전 상태를 Chroma와 분리 |
| 파싱 | Apache POI | PPTX 구조 접근에 적합 |
| OCR | Tesseract 또는 외부 OCR API | 이미지 기반 인포그래픽 보강 |
| 임베딩 | 사내 표준 모델 또는 외부 API | 검색 품질 결정 핵심 |

## 핵심 설계 원칙

1. 검색 단위는 `document`가 아니라 `slide chunk`다.
2. 각 chunk는 반드시 `slide_no`와 `document_id`를 가진다.
3. 질의 응답은 `답변 생성` 이전에 `근거 슬라이드 목록`을 먼저 확정한다.
4. 인포그래픽 보강을 위해 슬라이드 전체 요약 chunk를 별도로 저장한다.
5. 프로세스 슬라이드는 `workflow graph`를 별도 추출 계층으로 가진다.
6. 업로드와 질의는 동기 API처럼 보여도, 내부 인덱싱은 비동기 배치로 분리한다.
7. 추출 품질은 골드셋과 retrieval 지표로 계량해야 한다.
8. 답변 가능성이 낮으면 no-answer를 반환하는 보수 정책을 기본으로 한다.
